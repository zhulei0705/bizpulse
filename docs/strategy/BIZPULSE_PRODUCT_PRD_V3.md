# 商脉 BizPulse 3.0 产品 PRD

> BIZ-V3-01：原采购技术设计保留；跨行业客户能力、D0–D3和商业匹配以文末增补为现行准备规则。只形成 PRD 和人工可测试规则，不实现正式引擎。

日期：2026-10-09。产品基线与概念设计，非 T10-C2 详细技术设计或开发授权。T10-C1.2 无通过依据，T10-C2 继续 BLOCKED；本轮不新增模型、迁移、接口或前端。

## 一、目标与用户流程

近期目标：让客户用更少筛选时间，得到有事实依据、满足自身能力约束的需求候选，并清楚知道还缺什么。长期定位：中国企业 AI 商业增长网络。首轮指标为可追溯性、误报、人工成本、客户处理行为与真实付费，不以页面数量、Signal 数量或总分衡量商业成功。

使用者：供应商销售负责人、技术售前、投标人员；运营研究员整理材料；人工审核员对证据和结论负责。采购方确认需求与资格时必须保留真实渠道和原话，不代替其做事实声明。

流程：客户授权能力资料与排除条件 → 需求雷达发现候选 → 六道硬门槛 → 参数逐项比较 → 商机证明书草稿 → 人工复核 → 客户授权交付 → 客户真实反馈。关键词和向量仅用于召回，不能决定匹配通过、批准或发送。

## 二、事实语义与状态分离

|标签|定义|显示规则|
|---|---|---|
|FACT|可信来源直接陈述的事实，绑定版本与原文位置|“厂商手册标称”不显示为独立实测；客户陈述标明陈述者与时间|
|INFERENCE|由明确事实及版本化规则得到的分析|展示输入、比较规则、适用配置及限制，不能伪装成采购方原话|
|UNKNOWN|缺失、冲突、无许可、过期或证据不足|显式列缺失项与人工核实问题；不得静默补预算、日期、参数或资质|

分别显示技术匹配状态、项目生命周期、非技术资格状态、证据审核状态、客户接受状态、可行动状态；其中任何一项不能替代另一项。技术 MATCH 不等于具备投标资格，客户喜欢卡片不等于采购方有购买 BizPulse 的需求。

## 三、四个产品模块

### 1. 需求雷达

用户场景：销售每天从多个公告中查找新项目，先知道谁有真实需求、项目何时有效，避免历史中标和重复公告占用时间。

输入：获许可的官方采购公告、意向、澄清、公司新闻和招聘；客户授权导入需求；来源许可、发布时间、采集时间、采购方及代理角色。输出：去重后的需求候选、生命周期、来源链、预算/截止及未知项、下一次核验动作。

真实来源要求：官方原公告/附件优先；聚合数据需许可并尽可能回链原始来源；robots 通过不替代条款和授权检查。只有需要 JS 且允许时启用可选 Crawl4AI；不能用浏览器取到页面证明合法。PDF 无有效解析策略则正文 UNKNOWN，不把占位文字当事实。

FACT：公告原文的采购人、日期、金额；INFERENCE：项目关联或事件类别；UNKNOWN：附件缺失、日期时区未知、匿名主体。新闻扩产和招聘最多构成需求线索，不能直接认定采购预算或采购计划。

业务规则：来源主体与业务主体分离；采购方、供应商、中标方、代理各设角色；预算与中标金额分开；采集时间不替代公告时间；跨公告关联必须有项目编号、采购方等可说明依据，冲突人工审查。意向是培育候选；已截止、已中标、取消仅历史研究。

人工边界：研究员处理来源诊断、主体与关联疑点；审核员确认版本/日期/阶段；不自动 APPROVED。商业价值假设：减少过期、重复和主体误报。验收目标：受控真实业务样本20–30 URL；不足如实报告。对送审关键字段准确率目标≥95%、证据回溯100%、严重主体错误0；任何严重错误立即停批，不能平均掉。样本选择、缺失数和分母必须公开。

### 2. 企业能力护照

用户场景：售前提供“能做什么、不能做什么、在哪些条件下能交付”，避免企业名字或主营关键词被系统当作能力证明。

输入：客户授权的企业身份、具体型号与配置、官网参数页、版本化手册、资质证书、实际交付地区/周期、售后条件和排除规则。输出：授权范围内的能力条目、适用条件、来源日期、有效期、负责人确认及缺失清单。

真实来源要求：产品参数来自官方页/手册或可靠原始资料；客户提供的非公开文件要标明授权、机密级别和使用范围。客户自述产能或交期仅证明其陈述，若未经独立核验须标记“客户陈述/待核验”；不能把历史中标推定为当前供货或购买 BizPulse 意愿。

FACT：某型号某配置标称能力、证书正文及签署声明；INFERENCE：经规则归一的比较值；UNKNOWN：条件、单位、有效期或当前交付版本缺失。不同型号/波长/工况不能拼接成一台万能设备。

业务规则：先确定法律主体与供货角色；生产商、代理商、服务商分别记录授权链；能力属于具体配置与条件。每个硬参数均有证据，客户排除规则版本化；证书到期失效不沿用。客户撤回授权后停用并按已约定保留/删除规则处理，不用其商业机密服务竞争对手。

人工边界：客户负责人确认资料与授权；审核员核验适用范围，不能代替采购资格审核。商业价值假设：降低错误推荐和重复问询。验收目标：先取得3份真实授权护照；拟用于 MATCH 的关键参数来源覆盖100%，型号混用0，过期资质当有效0；资料不足可交缺失报告，不填造字段。

### 3. 商机证明书

用户场景：销售与技术售前在5分钟内判断“为什么值得处理、哪里不符合、下一步核实什么”，并能打开原文复核。

输入：已过硬门槛的需求、能力护照、双边证据及规则版本；另保留 PARTIAL/UNKNOWN 的核实队列。输出：技术结论、逐项比较、非技术资格、生命周期、风险、人工审核与建议动作；最多5张高相关卡/供应商/交付批次是上限，不是保底。

真实来源要求：需求侧与供给侧分别引用对应版本，产品引用不能替代采购要求引用；缺失快照和错位引用隔离，不能反向改原文迎合引用。

FACT：采购内容、厂商参数、截止等；INFERENCE：比较结果和行动建议；UNKNOWN：投标准入、报名、价格、未见附件及最新更正。MATCH 只覆盖已识别的适用关键硬参数且需求完整性已确认；不能隐藏尚未识别的关键附件。

业务规则与人工边界：审核员签名批准证明书；批准内容不等于授权触达。任何原文/Evidence 不一致或严重归属错误立即停止；历史中标不得进入当前可投标队列。客户只能按实际行为确认接受，不自动建立 Interaction 或成交。

商业价值假设：提供可审计的销售决策材料。验收目标：每批至少双人复核5–10个真实比较；不足则全检并标不足；全部关键引用可回放，错误行动卡0；客户能复述匹配与缺口，目标≥4/5受测用户在5分钟内完成，实际分母不足不判通过。

### 4. 价值反馈闭环

用户场景：客户指出“不相关、过期、资料不全、已知、值得跟进”，产品区分数据错误、技术不符和商业价值不足。

输入：经授权的客户原话/表单、人工实际行动、真实报价/合同/到账凭证及原卡版本。输出：反馈原因、纠错任务、客户队列成本/使用/续费统计、拟调整规则；不推断客户回复或成交。

真实来源要求：陈述人、日期、渠道、原话与授权；金额分开记录报价、合同和到账；内部目标不是实际结果。FACT：已发生反馈、行动及付款；INFERENCE：价值归因假设；UNKNOWN：客户未回应、成交是否由本产品促成。

业务规则：一个项目对同一客户的重复卡不能重复算认可；客户接受、实际处理、采购成交、BizPulse 付费分别计数；无回复不是负面反馈也不是认可。规则调整先离线复核并人工批准，不能因单次反馈绕过硬门槛。

人工边界：人工确认原话与实际动作后记录；本轮不写正式业务记录。商业价值假设：形成真实纠错与续费依据。验收目标：每个付费试点至少一次可核验复盘；送达/已回应/未回应分别报告，关键反馈来源覆盖100%；首轮至少2家真实付费，续费按到期队列计，尚未到期标未验证。

## 四、跨行业硬门槛与排序

|门槛|PASS 所需事实|FAIL|UNKNOWN 的处理|
|---|---|---|---|
|需求真实性|来源允许，采购角色明确，需求原文可核验|伪造、错归属、违规源|隔离或补证，不进合格排序|
|事件时效性|当前阶段及对应允许动作确认；截止/报名仍适用|截止、中标、取消作为当前投标|待核实；意向单独培育，不声称可投标|
|供给能力|具体配置与供货身份可信|明确无相应能力/授权|补资料，不能靠企业名填补|
|技术/资质硬约束|适用硬参数、资质、报名等逐项确认|至少一项明确不满足|技术可 PARTIAL，但当前投标准入待确认|
|地区与交付|交付地点、周期、服务及边界可满足|明确不能交付|待客户确认，不能默认全国覆盖|
|客户排除规则|已取得客户版本化规则且未触发|禁入地区、客户、产品等被触发|先获取规则，不能默认无排除|

六门槛均 PASS 的候选才能在相应动作队列排序。技术匹配可独立计算，但不能通过高分抵消资格、时效或证据失败。UNKNOWN 队列可以按补证截止和人工工作量安排核实顺序，不能称合格商机排名。

排序概念：适配深度、时效余量、客户优先、交付确定性、增量信息价值；初期由人工给明确理由，不新增黑箱模型。后续权重需客户验证，数值分数不表示成交概率。预算未知不得估作事实；预算不是硬要求时可以 UNKNOWN，若客户明确设硬预算门槛则必须确认。

规则包按需求类型与客户能力选择：设备以工艺/尺寸/功率/精度/材料/资质等为主；服务以范围/人员资格/工期/SLA 等为主。共有证据、状态和授权规则；不把激光、某地区或某公司写成全局准入限制。新增行业先人工规则样本验证，不自动扩量。

## 五、逐项技术比较定义

1. 确认需求范围、完整附件、标包和适用硬参数；未确认完整性不输出 MATCH。
2. 对每项保存原值、单位、操作符、工况、硬/软标记与需求引用。客户排除与采购硬条件分开。
3. 同一型号配置取得产品值、单位、条件与产品引用；不跨型号拼接。
4. 比较等值、集合包含、上下限、区间、尺寸逐轴及明确公差；单位只能用审核过的转换表，保留转换前后值。不可比较、非有限值、单位或工况不明为 UNKNOWN。
5. 逐项 SATISFIED / UNSATISFIED / UNKNOWN，生成可回放说明，不让语言模型补参数或直接批准。

|结论|聚合条件|显示限制|
|---|---|---|
|MISMATCH|至少一个适用关键硬条件有可靠证据证明不符|针对所比较配置，不推断全公司都不能供货|
|MATCH|有足够需求、完整性确认，所有已识别适用关键硬参数有可信产品证据且满足|仍列非技术准入待核实；不等于可投标|
|PARTIAL|部分参数已满足，但还有硬参数、需求完整性或条件待确认|不称通过硬门槛|
|UNKNOWN|没有足够可比较证据、空需求或无法确认匹配范围|不等于明确不符合|

软条件不满足单列偏差；不能把营销关键词当关键技术证据。明确硬条件不符优先于未知；证据冲突且无法确定哪份有效时保持 UNKNOWN，交人工处理。MISMATCH 与 UNKNOWN 都不得通过语义高分变成 MATCH。

## 六、生命周期与行动

生命周期概念：INTENTION（意向）、TENDER（招标）、CLARIFICATION（澄清）、CLOSED（截止/结束）、AWARDED（中标）、CANCELLED（取消）、UNKNOWN。跨公告关联依证据，不仅靠标题相似。澄清保留底层阶段并更新经确认的有效条件；不能只因有更正就把已结束项目重新开放。

原公告日期、采集时间、有效截止、报名期和预计采购月份分别保存；未知不互相替代。意向过预计月份只提示待复核，不能猜测成交。采购方、代理、中标方不同角色独立标记。

可行动类型：培育核实、投标准入核实、准备投标、历史研究、停止处理。只有有效招标、报名及技术/资质/交付门槛已确认并人工复核，才能标“准备投标”；其余明确限制。此概念不改变现有 Opportunity 状态，也不恢复汉邦隔离机会。

## 七、概念数据与证据合同

以下是文档字段需求，不是数据库迁移设计：

|对象|最小字段需求|复用与缺口|
|---|---|---|

|比较说明|双边版本、操作符、转换、逐项状态、聚合理由、缺失及规则版本|复用 Evidence/风险说明；计算记录持久化待后续评估|

证据链：原始 URL、最终 URL、采集时间、来源域名、许可依据 → 原始响应/快照版本和哈希 → 明确文本版本 → Unicode 字符偏移 [start,end) 与原文引用 → 解析/规则版本 → 比较结果 → 审核人/时间 → 交付卡版本。

原始字节、原始可见正文、清洗正文不能同名混用。引用必须等于目标版本文本切片；重清洗产生新版本，不覆盖旧引用。网页后来变化不修写历史快照。快照不存在、哈希不符、偏移错误、归属冲突即隔离并阻断下游。来源可靠度和引用完整性分别校验，高可靠域名也不能放过错引用。

## 九、质量与商业验收

所有下列阈值是验收目标，当前达成情况未验证。规则测试可用隔离测试样例，商业指标只能用真实合法资料；二者不能混计。

|指标|分子/分母与口径|目标与停止|
|---|---|---|
|证据可回溯率|准确切片、哈希/版本及快照均可验证的关键引用÷受检关键引用|100%；任一不一致立即停批|
|字段准确性|人工核对正确的已填关键字段÷已填且审阅字段|≥95%；另报缺失比例，禁止用全部 UNKNOWN 获高分|
|合格精确率|双人复核真正通过对应动作门槛的输出÷系统声称合格的全部输出|首轮≥90%，分歧裁决；严重归属/行动错误0|
|误报/漏报|固定真实候选池内，分别判关键词基线与参数流程，对照同一人工真值|报 TP/FP/FN/TN；没有完整标注池就标漏报未验证|
|客户接受率|客户明确愿意处理的唯一项目卡÷客户已明确评审的唯一卡|目标≥60%；未回复另报，不能剔除后称全部认可|
|筛选时间|同一任务/固定池、不同顺序对比旧流程与证明书的计时|目标中位数下降≥30%；样本与难度不一致不做因果结论|
|付费及续费|实收试点客户、已到期实际续费客户÷已到期客户|先2家付费；续费目标≥50%，小样本只作方向证据|

首轮20–30 URL 和5–10比较复核只是有限样本，不足以证明跨行业性能。报告计数、来源分布、缺失与分歧，比例可附二项置信区间；零次严重错误不代表风险为零。测试/试验失败保留，不补造样本。

## 十、交付与开发边界

立即：人工模板、来源目录、授权清单、访谈与成本记录；不修改业务库。Gate 后且经人工授权：验证真实来源、制定 T10-C2 详细设计与小范围实现，继续复用 FastAPI/SQLAlchemy/现有前端和证据审核，不另起数据库或大型 Agent 框架。实际付费后再评估专属集成、企业权限、复杂计费和规则规模化。

当前非目标：自动营销、自动批准、自动成交、全功能 CRM、交易市场、未经许可数据销售。本 PRD 不自动成为开发任务。关联 [商业模型](BIZPULSE_BUSINESS_MODEL_V3.md)与[90天验证](BIZPULSE_90_DAY_VALIDATION.md)。

## 十一、BIZ-V3-01 客户能力护照 PRD

Customer Capability Profile 的对象是未来付费客户，不是潜在采购方。最小载体为客户授权 Markdown/表格及证据附件索引，不增加数据库表、不要求填完整长问卷才能访谈。首次15分钟先收主体、主要产品/服务、能解决的问题、目标客户、交付边界、排除及三个痛点；有合作意向后补参数、资质和案例。

完整字段包括企业基本信息、产品与服务、能够解决的问题、真实成功案例、目标客户类型、优势、技术能力、交付地区、必要资质、可接受项目规模、不承接业务、当前商业目标、获客方式、已有工具和三个优先问题，均见[最小采集模板](BIZPULSE_CUSTOMER_CAPABILITY_TEMPLATE.md)。

每个字段采用两个独立维度：来源标签 CLIENT_PROVIDED（客户提供）/OFFICIAL_VERIFIED（已由官方来源核对）/AI_INFERRED（AI推断）/UNKNOWN（不清楚），及语义 FACT/INFERENCE/UNKNOWN。客户提供只能确认“客户如此陈述”，不等同独立验证。官网营销声明只确认其披露；AI推断不能作为硬约束通过依据。客户陈述与官方冲突时保留两者及人工裁决，不覆盖原话。记录负责人、授权、版本、日期和更新触发条件。

## 十二、D0–D3 需求真实性分级

等级与匹配状态、生命周期、客户反馈、生产 Signal 状态分离。本阶段由人工按下表判定，不改现有 Signal 算法。

|等级|必要依据|缺失/限制|允许动作|
|---|---|---|---|
|D3 明确需求|身份/需求角色明确，可信原文直接表达相关商业需求，原文版本完整，发布时间和当前事件状态已核实|缺预算不自动降级，预算仍 UNKNOWN；是否能投标/联系单独核实|可进入客户相关性核验；不是自动合格机会|
|D2 强变化|可信来源明确重大扩产、新业务/设施等强变化，主体、日期、状态可核验且与客户能力相关|具体采购事项和意图尚未确认|人工核实需求；不展示为明确采购|
|D1 需求假设|仅有可解释但间接/普通的变化或关联依据|需求、时效等尚不确定；普通招聘通常最多 D1，不能由 LLM 升 D3|研究/访谈待核实，不计有效商机|
|D0 缺可靠证据|没有可靠来源、主体/原文不可确认、仅关键词或引用无效|疑似伪造/违规/错归属隔离；不是靠低置信度补救|不推荐跟进；严重问题停批|

判定顺序：许可/完整性 → 来源真实性 → 业务主体与角色 → 发布时间 → 状态/生命周期 → 业务相关性 → 原文是否直接表达需求。LLM confidence 不参与升级。缺日期或状态无法核验时不能 D3/D2，至多 D1；证据本身无效为 D0。证据明确但已结束的历史需求可标“历史 D3”，当前行动为历史研究，不能计当前需求或可投标。合同授予不构成供应商购买 BizPulse 意图；普通招聘也不构成明确购买软件/设备意图。

有效期按需求类型及实际截止设定并说明，不全局任意设“最近30天就有效”。D3不强制只有采购公告：授权的真实客户需求说明也可直接表达，但保留客户来源与核验边界，不包装成官方核验。

## 十三、商业供需匹配规则与人工测试表

先检查七项：主体真实、需求证据有效、事件仍具跟进价值、产品/服务能力符合、必要资质、地区/交付条件、客户排除。每项 PASS/FAIL/UNKNOWN；确实不适用标 N/A 并记录原因与审核人，不可默认缺资质就是 N/A。

关键项 FAIL → MISMATCH/不推荐；UNKNOWN → PARTIAL 或 UNKNOWN/待核实，不能完全匹配；全部适用硬项 PASS 后才评估需求适配、价值、时效、获客成本、公开渠道和当前交付能力。资格待核实不强行判不符，但不得完全匹配。缺公开渠道本身不证明没有需求，渠道 UNKNOWN 则暂不建议触达；付费客户提供的授权渠道与公开渠道分别记录。

完整匹配与技术 MATCH 分别显示：原文“技术 MATCH”定义保留，商业完全匹配还需对应动作的全部门槛通过。D2可以是“能力适配/需求待核实”，不能称已确认商机；D1/D0不能计入确认有效机会。潜在价值与 CAC 分开列假设、来源和未知，不以 AI 金额预测当事实。

以下是人工判例输入条件，不是实际客户或测试结果，也不创建数据：

|条件组合|需求/匹配期望|推荐动作|
|---|---|---|
|原文有效、明确仍开放需求、全部适用硬项核实通过|D3，商业完全匹配；技术条件另列|人工复核后建议跟进|
|同上但必要资质无证明|D3，PARTIAL/资格 UNKNOWN|补资格，不称完全匹配|
|确定交付地区不可满足或触发客户排除|证据等级不改变，MISMATCH|不推荐，列具体排除|
|只有普通招聘及 LLM 高置信度|最多D1，需求 UNKNOWN|不计有效机会|
|强扩产事实但未说明购买事项|D2，具体需求待核实|人工询问，不能预测预算作事实|
|历史中标公告、今天采集|历史事实，不构成当前购买意图|历史研究，不推荐当前投标|
|Evidence 切片不等于原文或主体误归属|D0/隔离，匹配阻断|立即停批|
|全部条件通过但客户此前已知|真实性/能力不变，增量价值不成立|标已知，去重统计|

验收采用真实经许可资料人工复核；规则表只是规范，不声称已执行商业测试。[商机证明书模板](BIZPULSE_OPPORTUNITY_PROOF_TEMPLATE.md)包含14项交付字段、拒绝推荐与真实反馈状态；[首批客户计划](BIZPULSE_FIRST_PAID_CUSTOMER_PLAN.md)定义计量。不得把人工文件评分写回正式 Opportunity 公式或自动批准 Signal。
